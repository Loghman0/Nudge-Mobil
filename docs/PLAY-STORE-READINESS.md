# Android release gates — 8 November 2026

Nudge is being built as an independent native Android application. A standalone test APK exists; this is not a completed mobile port or a Play Store release. The owner intends to publish when the app is ready. Do not publish, create a paid developer account, accept store agreements, or generate the final signing identity as part of an ordinary preview build.

This checklist distinguishes source/build work from installed-device evidence. The exact state of each delivered APK belongs in [VERIFICATION.md](VERIFICATION.md); feature coverage belongs in [PARITY.md](PARITY.md). An unchecked item remains a release gate even if a unit test or web test passes.

0.8.1 checkpoint: standalone APK and test-signed AAB exist; bundletool validation, matching APK/AAB native/DEX/Hermes payload and static16KB checks pass. Real Redmi Google return/session retention, daily answer save and generic push receipt/app-opening have bounded evidence. The AAB uses Android Debug signing and must not be used as the final Play upload identity. No store upload, production access or Play-generated installation is claimed.

## Identity and distributable

| Gate | Current evidence / required action |
| --- | --- |
| Final application ID | `com.projectnudge.app` is provisional. Settle the ID before the first Play upload and keep it stable for subsequent updates. Renaming the public brand does not require changing this ID. |
| Store signing | The initial APK uses the generated Android test signer. Prepare a separate protected upload key and Play App Signing when release is authorized. Do not commit a keystore, password, service account, or store token. Back up the upload-key recovery information securely. Android documents the distinction between an upload key and the app signing key used for delivered installations. [Signing guide](https://developer.android.com/studio/publish/app-signing). |
| Store artifact | Produce and validate a signed Android App Bundle (`.aab`) for Play; keep APKs for direct installation tests. New Google Play apps use App Bundles. Test the Play-generated installation and an update from the previous track build, not only a locally assembled APK. [App Bundle guide](https://developer.android.com/guide/app-bundle). |
| Versions and SDK | Increment `versionCode` for each uploaded build. The first verified APK targets API 36 and supports ARM64. Google's policy checked on 8 November 2026 requires new phone apps and updates to target API 36 or later. Recheck the requirement at the actual release date, then inspect the final bundle's manifest; compile SDK alone does not establish the target. [Target API policy](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en). |
| Native dependencies | Resolve or document each supported-toolchain audit finding; review the final merged permissions and bundled SDK behavior. Verify native libraries against current Play checks, including page-size compatibility, on the uploaded artifact. A clean source scan does not establish a clean installed runtime. |
| Store identity | Confirm rights to the name/logo, prepare real phone screenshots, icon and feature graphic, accurate description, category and content rating. Do not present speculative personality reflections as clinically validated assessment, diagnosis or prediction. |

## Accounts, privacy and data control

- [ ] Complete native Google sign-in, return-link validation, cancellation, process interruption, token refresh, revoked-session handling and sign-out on an installed APK. Use the existing Supabase accounts; keep client configuration public and all administrative/AI keys on the server. Decide the final callback strategy before store review and test it with the actual signing/distribution configuration.
- [ ] Prove the preview handoff: explicit review before save, encrypted local draft/session storage, 24-hour draft expiry, same-account binding, stable retry identity, no resurrection of deleted evidence, and no automatic save after account switching.
- [ ] Complete the native privacy controls and owner-scoped export/deletion transports. Verify exclusion, correction, forgetting, full deletion and cross-device changes using disposable records. Signing out is not account deletion.
- [ ] Provide an easy-to-find in-app account-deletion path and a working public web resource to request account and associated-data deletion without reinstalling the app. A privacy-policy link alone is insufficient. The present web profile deletion action is a useful backend starting point, but an unverified browser fallback is not recorded as a completed mobile requirement. State any legitimately retained data and its actual retention period. [Google account-deletion requirements](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en).
- [ ] Finalize accurate public notices using the real operator/support contact, processing locations, vendors, retention and backup behavior. These details were deferred for the web demo; do not fill them with invented values or describe the public-launch flag as access control. Keep a reachable HTTPS privacy policy and deletion resource in both the app and listing.
- [ ] Complete Data safety from observed behavior and the final dependency inventory, including Google/Supabase authentication, saved answers and reflections, any user-written content, operational logs, optional metrics and future AI/push providers. Determine each category and purpose from the actual release; do not select “no data collected” because the preview can run offline. Include SDK collection, encryption/deletion claims and optional versus required behavior. Closed/open/production tracks require the form; exclusively internal-track apps are exempt from that section. [Data safety guidance](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en).
- [ ] Keep optional AI off until server credentials, explicit consent, provider processing/retention, accounting limits and usable failure paths are verified. Google-only signup is the current demo choice; public email signup remains disabled until a verified SMTP sender and real recipient delivery checks are complete.
- [ ] Request notification or other runtime permissions only in context. Do not add advertising, tracking, camera, contacts or microphone access merely because a library supports them. Native notification delivery, quiet hours and opt-out must be tested separately from web push.

## Product and installed-device acceptance

Record device/OS, build hash, steps, result and evidence for each row. At least one real mid-range Android phone is required in addition to any emulator tests; also cover a smaller phone, a large screen and the supported oldest/current OS range.

| Area | Required verification |
| --- | --- |
| Core journey | Preview → reflection → Google sign-in → review/save → Today → About you → correction/exclusion/deletion. Verify the same account state on web and phone. Complete Decide and supporting parity rows before calling this the complete mobile version. |
| Accessibility | TalkBack labels, selected/disabled/busy states, reading/focus order, Back/cancel, at least 48 dp targets, largest font, display scaling, bold/high-contrast settings and the approved light-only theme. Check small widths, landscape, safe areas, keyboard overlap, long answers and RTL content. Source contrast tests are only one part of this. |
| Failure and recovery | Airplane-mode preview; offline account requests; slow/interrupted connections; duplicate taps; lost success responses; conflict after web edits/privacy reset; cancelled auth; expired/revoked tokens; process death during login/save; switch account; unavailable question bank; pause/exhausted pool. Pending must not be reported as saved. |
| Performance and stability | Cold/warm launch, long-session memory, scrolling large answer lists, keyboard interactions and background/resume on a real phone. Measure crashes/ANRs and frame behavior. Avoid collecting private answer text or tokens in diagnostics. |
| Android distribution | Fresh install, launch without Expo Go/Metro, deep link from browser, system Back, rotation, upgrade preserving intended data, uninstall/reinstall behavior and final merged permissions. Verify encrypted-store backup exclusions on the actual build. |
| User value | Have testers explain what a reflection is based on, correct something that does not fit, change a topic, and find data deletion. Record observations separately from hypotheses; successful tapping is not evidence of psychological validity or useful insight. |

## Play Console and release procedure

1. When the owner is ready, complete the applicable developer identity/account setup and verify the account's actual requirements. For personal accounts created after 13 November 2023, the policy checked on 8 November 2026 requires a closed test with at least 12 opted-in testers continuously for 14 days before applying for production access. Meeting the duration is not automatic approval. Plan authentic test tasks and feedback; do not fabricate testers or results. Recheck the account's dashboard and [current testing policy](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en) at that time.
2. Upload the authorized signed bundle to an internal track first. Inspect automated/pre-launch findings, test real installations, then use the closed track and remedy the failures. Provide reviewers working app-access instructions and a permitted disposable test account if needed; keep credentials out of source and public listing text.
3. Complete privacy/Data safety, account-deletion link, content rating, target audience, app access and any other declarations shown for the actual app. Review health-related or AI declarations against the product's real features rather than assuming either applies or is exempt.
4. Confirm the final backend configuration, monitoring, support response, deletion process and recovery procedure. Capture a release evidence bundle with artifact/hash, test matrix, known limitations, dependency review and rollback/update plan.
5. Obtain explicit owner approval for the concrete store listing and release, then submit. A successful build, an APK download, or a completed closed test does not guarantee Google approval or authorize public rollout.
